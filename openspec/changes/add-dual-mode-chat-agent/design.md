# Design: add-dual-mode-chat-agent

## Context

绿地项目，无遗留代码。定位为**宿主系统中的双模式对话智能体模块**：普通对话直答 + 工作模式 Agent 产出可预览/可修改/可下载的产物。**鉴权由宿主系统负责**——本模块不做注册/登录，通过可信 `X-User-Id` 头接收身份并做数据隔离。团队技术背景偏 Vue + Element Plus 前端；后端经探索从 Java 调整为 Python（原因见决策 3）。部署路径明确：本地 docker-compose 起步，后期迁服务器，代码不动只改配置。模型选定 GLM（智谱，OpenAI 兼容协议）。

## Goals / Non-Goals

**Goals:**

- 双模式会话：普通对话（LLM 直答流式）/ 工作模式（Agent 完成任务 → 预览 → 增量修改 → 下载）
- 通用型产物：文档、表格、PPT、海报、数据结果
- 对外产品的基础约束：多用户、数据隔离、安全加固、用量埋点
- 本地起步可平迁服务器的架构（无状态后端、存储抽象）

**Non-Goals:**

- 计费/支付（只埋点不扣费）
- 管理后台、团队/组织功能
- 多 Agent 协作编排（v1 单 Agent 工具循环）
- 移动端/小程序（仅 Web）
- 对象存储实际接入（预留接口，本地磁盘实现）

## Decisions

### 决策 1：消息语义由状态机决定（"消息即指令"）

工作模式下用户与 Agent 共享一条持续对话流，消息含义由 Agent 当前状态决定：

```
┌──────┐ 新任务  ┌──────────┐ 完成   ┌──────────────┐
│ 待命  │──────▶│ running  │──────▶│preview_ready │◀─┐
└──────┘        │(工具循环) │       │(interrupt暂停)│  │
   ▲            └────┬─────┘       └──────┬───────┘  │
   │    执行中消息=转向 │          修改指令=增量修改─────┘
   └──────── 满意→下载,回待命
```

**理由**：执行中插话（steering）与预览后反馈（revision）统一为一个机制——用户消息注入 Agent 对话流，无需两套交互。产物修改默认跟随**最近一个产物**。
**替代方案**：为"修改"设计独立交互通道——被否，交互割裂且实现翻倍。

### 决策 2：智能路由识别到任务 → 弹卡片确认，不自动执行

普通对话模式下，轻量分类器（小模型/规则）判定消息是"闲聊"还是"任务"。判定为任务时弹确认卡片："这看起来像一项工作，要用工作模式处理吗？"确认后消息原样带入工作模式。工作模式下则不做判断，全部交给 Agent。

**理由**：误判成本不对称——把闲聊错当任务会浪费 Agent 执行成本并打断对话；卡片确认一键切换，体验顺滑（ChatGPT canvas / Claude artifact 同款模式）。
**替代方案**：静默自动派给 Agent——被否，误触发代价高。

### 决策 3：后端 Python / FastAPI 单体（放弃 Java）

**理由**：产物工具链（pandas、matplotlib、python-pptx、openpyxl、python-docx、playwright）全部是 Python 生态。Java 方案必须拆"Java 编排 + Python 干活"双服务加 HTTP 桥；Python 单体让大脑与手脚合并，一个代码库一种语言。
**替代方案**：Java (Spring Boot + Spring AI)——架构可行但双服务桥接成本永久存在，已否决。

### 决策 4：Agent 框架用 LangGraph

**理由**：本产品的核心难点是**有状态、可暂停恢复的 Agent 流程**。LangGraph 的 `interrupt()` + Checkpointer 恰好原生支持：图执行到预览节点暂停、全状态落库（Postgres）、用户反馈后恢复注入。生产成熟（1.0 GA），HITL 是其设计核心。
**替代方案**：Pydantic AI（类型安全优秀，但 HITL/检查点非其核心强项，可作后备）；OpenAI Agents SDK（轻量循环，状态机超出舒适区）；Dify（平台化配置，自定义状态机受限）；CrewAI（多角色原型向，控制粒度不足）。

### 决策 5：产物版本链 = LangGraph 一条 thread 的检查点历史

增量修改 v1→v2→v3 不自建版本管理：每次修改 = 恢复同一条 thread + 注入反馈消息，检查点历史天然构成版本链与审计记录。产物文件本体按 `{user_id}/{task_id}/v{n}/` 存储，元数据入 PostgreSQL。

### 决策 6：预览策略 C——中间格式优先，按类型混合

| 产物类型 | 中间格式 | 预览 | 下载转换 |
|---------|---------|------|---------|
| 文档/报告 | Markdown | web 直渲染 | pandoc → docx |
| 海报/图片 | HTML | HTML 即设计媒介，直渲染 | playwright → png |
| 数据结果 | HTML 表格 | 表格预览 | openpyxl → xlsx |
| PPT/幻灯片 | HTML slides | 翻页预览 | pptx 转换器或 pdf（保真度降级可接受） |

**理由**：预览零额外基础设施（web 原生渲染 HTML/md）；下载时才做一次性转换。海报类产物 HTML 本身就是设计媒介，渲染保真度完美。
**替代方案**：A 全中间格式（PPT 转换是坑）；B 全最终格式+Office 渲染服务（预览设施重、增量修改=整文件重生成）。

### 决策 7：两种代码执行，只有一种进沙箱

- **可信代码**（我们写的工具函数：文件生成、格式转换、渲染）→ 后端进程内直接执行，快且简单
- **不可信代码**（Agent 现场写的数据处理脚本）→ 必须进 Docker 沙箱

**理由**：沙箱调用频率和资源开销降一个量级，攻击面最小化。

### 决策 8：沙箱加固清单（对外产品红线）

每任务独立容器；无网络访问；CPU/内存/执行时长限额；非 root 运行；产出文件大小限额；任务结束容器销毁。

### 决策 9：GLM 经 OpenAI 兼容协议接入，配置化

LangGraph 走 `ChatOpenAI(base_url=GLM端点)`。具体 GLM 版本是配置项不是架构决策（起步用当前最新稳定版，可随时换型号或换厂商）。

### 决策 10：对外产品的"第一天必须"清单

- 身份来自宿主系统注入的可信 `X-User-Id` 头：模块不建用户表、不做注册/登录；生产配置（`REQUIRE_USER_HEADER=true`）下缺失该头直接 401，开发态回退默认用户
- 每张表带 `user_id`（sessions/messages/tasks/artifacts/versions/usage_events，均无外键——身份归属宿主系统）
- 文件路径按用户分域：`/artifacts/{user_id}/{task_id}/v{n}/...`
- 存储藏在 `StorageService` 接口后（本地磁盘实现，后期换 OSS/S3 不改业务代码）
- 用量流水第一天就记（只记不扣）：每次 LLM 调用记 user/model/tokens/耗时/session/task
- 预览 HTML 一律进 `<iframe sandbox>` + CSP；下载用带过期时间的签名 URL；API 限流

**替代方案（被否）**：模块内建注册/登录 + JWT——与宿主系统职责重复，身份双源会产生漂移；模块边界保持"信任网关注入的身份"最干净。

### 决策 11：前端 Vue 3 + Element Plus + Vite；通信 SSE

对话流 + Agent 过程事件 + 流式回复用 SSE（单向足够，用户消息走普通 POST）。前端布局：左侧对话流（消息/过程/确认卡片），右侧产物面板（预览/版本链/下载）。
**替代方案**：WebSocket——被否，双向能力用不上，SSE 更简单且代理友好。

### 决策 12：PostgreSQL 一库两用

业务表 + LangGraph `AsyncPostgresSaver` 检查点同库，本地 docker 起，运维最小。

## Risks / Trade-offs

- [HTML slides → pptx 转换保真度不足] → 降级方案：下载提供 pdf；或该类型直接用 python-pptx 生成、预览用渲染图
- [执行中消息注入：LangGraph 不支持在长工具调用中间打断] → 消息入队，在工具循环每轮间隙检查并注入；**列为开发前 spike，第一周验证**
- [智能路由误判] → 卡片确认兜底，错误成本仅一次点击
- [Agent 产物预览 XSS] → sandbox iframe + CSP + 不带主站凭证，安全评审必过项
- [沙箱逃逸/资源滥用] → 决策 8 加固清单 + 限流 + 用量记录监控异常
- [LangGraph 版本演进] → 锁定版本，升级视为变更
- [本地→服务器迁移] → 存储抽象 + 无状态后端 + 检查点在 PG，迁移只动配置

## Migration Plan

1. 本地：docker-compose（backend + postgres + sandbox-runner + frontend）
2. 迁服务器：同一 compose 改为生产配置（存储卷/对象存储、HTTPS、限流），代码不变
3. 回滚：绿地项目无回滚负担；数据库变更走迁移脚本（alembic）

## Open Questions

- GLM 具体型号与档位（GLM-4.x 稳定版 vs 最新旗舰）——实现期定
- 产物保留策略（用户产物保留多久、配额多少）——上线前定，v1 不清理
- 智能路由的实现形态（规则优先 vs 小模型分类）——实现期 spike
- 注册方式（邮箱/手机号/第三方登录）——实现期定，v1 邮箱+密码
